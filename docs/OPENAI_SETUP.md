# OpenAI: настройка и постоянная история

Интегрированный код поддерживает `rules-v2` и серверный OpenAI-режим с оценщиком `evidence-v2`. HTTP-контракт и клиентский адаптер общие для обоих режимов; для frontend-разработки режим `rules` не требует ключа. OpenAI может использовать прежнее локальное файловое хранилище либо общий Postgres для облачных инстансов и списка попыток. Готовность опубликованного URL подтверждается отдельной проверкой капитана.

## Что делает модель

OpenAI интерпретирует свободный текст пользователя в существующий `NegotiationAction`. Ответ проходит Zod-валидацию, затем engine проверяет предложение по сценарию и рассчитывает договор. Принятие, отказ, counteroffer, деньги, часы и сроки определяет engine. `clientReply` формируется из фактического решения и публичных фактов сценария. Оценщик `evidence-v2` подключен и в OpenAI-режиме.

Интеграция использует [Responses API](https://developers.openai.com/api/reference/resources/responses/methods/create) и [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses). Запросы идут только на фиксированный `https://api.openai.com/v1/responses`; произвольный base URL не настраивается. Модель по умолчанию - [gpt-5.4-mini](https://developers.openai.com/api/docs/models/gpt-5.4-mini). Наличие ключа и доступ к модели не заменяют проверку реального запроса; результат smoke-проверки капитан сообщает отдельно.

## Настройка капитана

В актуальной рабочей копии установи зависимости через `npm ci` и создай локальный `.env.local`:

```dotenv
SCOPESHIFT_AI_MODE=openai
OPENAI_MODEL=gpt-5.4-mini
OPENAI_TIMEOUT_MS=20000
SCOPESHIFT_SESSION_SECRET=
SCOPESHIFT_STORAGE=file
# OPENAI_API_KEY=your_private_key_if_not_already_set_in_the_server_environment
# SCOPESHIFT_REPLAY_DIR=.scopeshift/replay
```

Заполни `SCOPESHIFT_SESSION_SECRET` собственным случайным секретом длиной не меньше 32 символов. С пустым значением запросы OpenAI-режима возвращают ошибку конфигурации. Ключ можно оставить в уже настроенном серверном `OPENAI_API_KEY`. Если его нет, задай его локально в `.env.local`. Значения не отправляются в чат, не коммитятся и не получают префикс `NEXT_PUBLIC_`.

| Переменная | Назначение |
| --- | --- |
| `SCOPESHIFT_AI_MODE` | `rules` по умолчанию; `openai` включает серверный provider |
| `OPENAI_API_KEY` | API-ключ, обязателен для `openai` |
| `OPENAI_MODEL` | Модель, по умолчанию `gpt-5.4-mini` |
| `OPENAI_TIMEOUT_MS` | Таймаут provider: по умолчанию 20000 мс, допустимо 1000-60000 мс |
| `SCOPESHIFT_SESSION_SECRET` | Стабильный секрет подписи cookie, не меньше 32 символов; обязателен для `openai` |
| `SCOPESHIFT_STORAGE` | `file` по умолчанию для постоянного локального сервера; `postgres` для общего хранилища |
| `SCOPESHIFT_REPLAY_DIR` | Каталог receipts в режиме `file`; по умолчанию `.scopeshift/replay` |
| `SCOPESHIFT_DATABASE_URL` | Отдельная серверная PostgreSQL-строка ScopeShift, обязательна для `postgres` |
| `SCOPESHIFT_DAILY_AI_CALL_LIMIT` | Общая дневная квота новых OpenAI-вызовов в Postgres-режиме; по умолчанию 200, допустимо 1-10000 |

Секрет сессии должен сохраняться между перезапусками и деплоями. В режиме `file` сохраняй также каталог receipts, в `postgres` - ту же БД. После изменения окружения перезапусти сервер:

```sh
npm run dev
```

Для возврата к автономному режиму задай `SCOPESHIFT_AI_MODE=rules` и перезапусти сервер. Ошибка OpenAI не переключает приложение в `rules` автоматически.

## Postgres и Vercel

Для общего постоянного хранилища добавь к серверной OpenAI-конфигурации:

```dotenv
SCOPESHIFT_STORAGE=postgres
SCOPESHIFT_DATABASE_URL=
SCOPESHIFT_DAILY_AI_CALL_LIMIT=200
```

Строку подключения выдает провайдер БД. Храни ее в серверном окружении или отдельном игнорируемом `.env*` файле. Не заменяй ей переменные других проектов и не выводи значение в отчет. Runtime использует `pg`, проверку TLS-сертификата и небольшой пул соединений; Vercel подключает управление жизненным циклом пула через `@vercel/functions`.

До запуска приложения примени версионированный SQL из `migrations/001_durable_history.sql`. Сначала проверь его на дочерней ветке БД, затем применяй тот же SQL к production. Для ручной миграции нужен прямой, не pooled URL в `SCOPESHIFT_DATABASE_URL`. Например, создай игнорируемый `.env.migration` с этой единственной настройкой и выполни:

```sh
node --env-file=.env.migration scripts/migrate-postgres.mjs
```

Скрипт отвергает `-pooler` hostname. Не меняй выданный провайдером hostname вручную; возьми прямую строку подключения в настройках БД. Миграция создает receipts, снимки попыток и общий счетчик AI-квоты. Схема не создается автоматически в каждом HTTP-запросе.

При `VERCEL=1` OpenAI разрешен только с `SCOPESHIFT_STORAGE=postgres`. Файловый адаптер остается для постоянного локального Node-сервера: локальная директория serverless-инстанса не считается общим хранилищем. Для Vercel нужны серверные `OPENAI_API_KEY`, `SCOPESHIFT_SESSION_SECRET` и `SCOPESHIFT_DATABASE_URL`; они не должны попадать в клиентскую сборку.

`.env*`, `.vercel` и `.scopeshift` исключены из Git; `.vercelignore` также исключает env-файлы, receipts и локальные артефакты из загрузки исходников. Production-переменные задаются отдельно в настройках хостинга. Публичный URL и его приемка описываются в отдельном deployment-отчете, а не выводятся из успешной миграции или сборки.

## История, retry и Replay

- Перед первым POST нужно установить сессию через `GET /api/session`. Endpoint возвращает `{ mode: "rules" | "openai", historyStorage: "browser" | "postgres" }`, не вызывает LLM и не кэшируется. В `openai` он выдает подписанную cookie.
- `getSessionInfo` и `negotiate` из `src/lib/client/api.ts` разделяют один незавершенный bootstrap между одновременными вызовами. Для прямого HTTP-запроса сохрани cookie от GET; POST без корректной установленной сессии получает `409 INVALID_HISTORY` до платного вызова.
- Первый POST содержит один пользовательский ход первого события. После ответа следующий POST содержит прежнюю историю и ровно один новый ход.
- Cookie сессии сохраняется автоматически при запросах через same-origin клиентский адаптер. В OpenAI-режиме она подписана; срок действия 30 дней с создания, `HttpOnly`, `Path=/api`, `SameSite=Strict`, `Secure` на HTTPS.
- При ошибке provider или storage сервер также сохраняет уже созданную корректную cookie, чтобы retry нашел прежние receipts.
- Обработанные ходы берутся из серверных receipts и не отправляются на повторную интерпретацию. Переданный старый префикс должен совпадать с уже сохраненным.
- Точный retry использует прежний `turnId`. Измененный суффикс Replay получает новые ID и отправляется по одному новому ходу за запрос.
- Если для старого префикса нет receipts в этой сессии, сервер возвращает `400 INVALID_HISTORY`. Он не достраивает отсутствующую историю новыми вызовами LLM.
- Изменение текста, префикса или версии для сохраненного ID дает `409 INVALID_HISTORY`. После смены модели или сценария начинай новую попытку с новыми ID. Смена секрета делает прежние cookie недействительными.

Receipts связывают подписанную сессию, сценарий, ход, модель/версию и точный префикс истории. Они содержат текст ходов и проверенные серверные результаты. Браузер отправляет историю текста и необязательный `attemptId`, а не доверенные действия или финансовые итоги. В Postgres атомарный `pending` claim фиксируется до модели, а готовый receipt - до успешного ответа. Разные инстансы используют одну запись и не интерпретируют один ход параллельно.

В Postgres-режиме UI передает `attemptId`, а сервер сохраняет соответствующий проверенный ответ как снимок попытки. Новая ветка Replay получает новый ID попытки, точный retry сохраняет прежний. Старый retry не сокращает более длинную сохраненную историю; изменение ее префикса под тем же ID дает 409. Неудачная запись снимка возвращает 503. Если receipt уже сохранен, повтор может дописать снимок без нового вызова модели.

`GET /api/attempts?scenarioId=...` возвращает до 20 последних измененных снимков текущей подписанной сессии, укладывающихся в общий JSON-лимит 3 MiB. Самые новые имеют приоритет; включенные элементы идут от старых к новым. Пропущенные строки остаются в БД. Ответ приватный, `no-store`, с `Vary: Cookie`; этот GET не создает сессию и не вызывает AI. Ошибка БД дает 503 вместо фиктивной пустой истории.

UI объединяет серверные снимки с браузерным кэшем, сохраняя локальные черновики. При недоступной серверной истории он показывает предупреждение, а браузерные попытки остаются доступны. Очистка `localStorage` допускает восстановление с сервера, пока прежняя cookie действует. При потере cookie, смене браузера или истечении 30 дней прежняя анонимная история не восстанавливается. Аккаунты, ссылки восстановления и перенос между устройствами не реализованы. В локальном файловом режиме снимки попыток остаются только в браузере; сервер хранит receipts для Replay.

## Ошибки и границы деплоя

Неполная конфигурация, недоступный provider, таймаут, отказ, невалидный структурированный ответ или недоступность persistence дают `503 AI_UNAVAILABLE`. Лимит provider дает `429 RATE_LIMITED` с `Retry-After: 60`. Ключи и raw body ошибок provider не возвращаются клиенту. Неподтвержденный результат не показывается как успешный договор; клиент сохраняет отправляемый текст для retry.

В Postgres новая попытка вызова OpenAI сначала резервирует общую дневную квоту. По умолчанию доступны 200 таких попыток в день UTC на весь деплой, лимит задается `SCOPESHIFT_DAILY_AI_CALL_LIMIT`. Кэшированные retry и Replay не расходуют новую квоту. Неуспешный новый вызов тоже может ее расходовать. Счетчик общий для всех инстансов и не сбрасывается заменой cookie. При исчерпании API возвращает `429 RATE_LIMITED` с `Retry-After` до следующей полуночи UTC. Процессное ограничение 30 запросов в минуту на cookie остается best-effort дополнением.

Если сетевой сбой, таймаут, неизвестная ошибка или остановка процесса оставляют результат вызова неопределенным, Postgres сохраняет `pending` claim и не запускает модель повторно автоматически. Невалидный ответ и отказ также не освобождают claim. Разрешено освобождение собственного claim только для проверенных ошибок конфигурации/лимита provider, общей квоты или истории до допустимой обработки. Для неоднозначного зависшего хода нужна новая попытка или проверка оператором. Автоматического перехвата по истечению времени нет.

Успешный OpenAI-ответ содержит `X-ScopeShift-Interpreter: openai-v1` и `X-ScopeShift-LLM-Model` с настроенной моделью. `X-ScopeShift-OpenAI-Calls` показывает число новых интерпретаций именно этого запроса: новый ход обычно дает `1`, точный retry - `0`. Оценка помечена `X-ScopeShift-Evaluation: evidence-v2`. Метка `X-ScopeShift-Scenario-Revision` связывает сценарий с моделью и версиями engine/prompt. После обновления engine до `simulation-v2` нужны новые попытки; старые receipts не переинтерпретируются под новыми ответами клиента.

Файловое хранилище сохраняет receipts на локальной файловой системе и использует прежние локальные lock-файлы. Оно не заменяет Postgres для serverless-инстансов. Наличие Postgres-адаптера снимает конфигурационный запрет Vercel только при корректной настройке БД; доступность опубликованного приложения все равно проверяется отдельно.

## Проверка

Обязательные локальные проверки остаются прежними:

```sh
npm run typecheck
npm run lint
npm test
npm run build
```

После запуска настроенного OpenAI-сервера выполни в другом терминале:

```sh
node scripts/smoke-openai.mjs http://127.0.0.1:3100
```

Адрес должен совпадать с адресом твоего сервера; обычный `npm run dev` использует порт 3000. Live smoke делает реальные запросы OpenAI. Сначала заверши настройку, затем проверяй свободную формулировку, неизменность retry и сохранение обработанного префикса после перезапуска. Успешные mocked-тесты сами по себе не подтверждают живое подключение.

После остановки и повторного запуска того же сервера можно проверить последнюю сохраненную smoke-попытку без новых обращений к модели:

```sh
node scripts/smoke-openai.mjs http://127.0.0.1:3100 --retry
```

Локальный smoke-артефакт содержит анонимную тестовую cookie и вымышленные ходы; он сохраняется в исключенном из Git `.scopeshift`. Если процесс аварийно завершился во время записи хода, оставшийся lock блокирует повторный вызов до проверки оператором. Активные блокировки не удаляются автоматически.

Для проверки настоящего Postgres задай `SCOPESHIFT_TEST_DATABASE_URL` прямой строкой к уже мигрированной дочерней ветке БД и запусти:

```sh
npx vitest run src/lib/simulation/postgres-replay-store.integration.test.ts src/lib/simulation/attempt-store.integration.test.ts
```

Это opt-in тесты: без переменной они пропускаются. Используются случайные синтетические идентификаторы; после проверки удаляются только принадлежащие тесту строки. Отдельно проверь приложение с `attemptId`, восстановление через `GET /api/attempts`, retry без новых AI-вызовов и сохранение префикса после перезапуска или нового деплоя. Проверка HTTP smoke без `attemptId` подтверждает receipts, но не создание снимков для списка попыток.

## Проверено 14 ноября 2026

Backend-прогон PR #3 на Node 22 включал успешные typecheck, lint, 108 обычных unit/integration-тестов и production-сборку. Реальный HTTP smoke с OpenAI разобрал написанные словами цены и сроки, прошел три события до результата $2,050 / 26 часов / день 7 с оценкой `evidence-v2` и отдельно обработал уточнение. Точный retry вернул прежний результат с `X-ScopeShift-OpenAI-Calls: 0`; сохранение receipts после перезапуска проверялось отдельно. Подробности и исправленные регрессии: `docs/EVALUATOR_INTEGRATION_QA.md`. После слияния выполнен полный локальный браузерный проход, а небольшие исправления UI прошли typecheck, lint, 111 тестов и build. Браузерная приемка и оставшиеся задачи записаны в `docs/DEMO_READINESS.md`. Теперь публичный OpenAI/Postgres-деплой проверен отдельно: https://scopeshift.vercel.app. Подробности: `docs/PUBLIC_DEPLOYMENT.md`.

Для нового постоянного хранилища версионированная миграция проверена на дочерней ветке Neon и применена в production-БД. Основной набор из 159 тестов и семь настоящих DB-тестов прошли: конкурирующие receipt-запросы, чтение из нового пула, зависший claim без перехвата, общая квота, сохранение и восстановление попыток, изоляция сессий, защита длинной истории от старого retry и конфликт измененного префикса. Локальный HTTP-проход с настоящим Postgres/OpenAI сохранил две попытки и проверил приватный список, Replay и точный retry. Повтор после реального перезапуска сервера также потребовал ноль новых AI-вызовов. После публикации проверены публичный HTTP-проход и браузерный сценарий. После повторного production-деплоя история сохранилась, точный retry потребовал ноль новых вызовов модели. Отчет: `docs/PUBLIC_DEPLOYMENT.md`.
