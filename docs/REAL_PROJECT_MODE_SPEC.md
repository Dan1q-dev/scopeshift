# Real Project Mode v1

## Цель и границы

ScopeShift сохраняет Practice Mode и добавляет применение навыков к собственному проекту: **Learn it. Apply it. Improve it.** Новый поток: **Paste agreement -> Analyze client request -> Review -> Calculate -> Respond**. Пользователь без обязательной регистрации сопоставляет запрос клиента с сохраненным договором, проверяет цитаты, исправляет трактовку и готовит предложение.

Это спецификация интеграционного среза, а не подтверждение production-готовности. Фактические проверки и неполные части капитан фиксирует после реализации.

P0 использует вставку обычного текста. Извлечение PDF/DOCX, OCR, email-рассылка, аккаунты и дополнительные сценарии не входят в первый срез. Интерфейс не должен показывать успешное извлечение файла, если оно не реализовано. Английский текст продукта сохраняется.

## Данные и источники

Типы и Zod-схемы: `src/types/real-project.ts`. Они не заменяют Practice Mode `ScopeItem`, `Scenario`, `ProjectState` и HTTP-контракт переговоров. REST-контракт: `REAL_PROJECT_API.md`.

Проект содержит название, введенные пользователем согласованные fee/hours/deadline и документы agreement/amendment. Исходный текст нормализуется один раз в `canonicalText`. Passages с устойчивыми ID и диапазонами относятся к этой версии текста. Индексы `start`/`end` используют UTF-16 code units JavaScript, начало включается, конец исключается. Цитаты сервер разрешает по реальной подстроке указанного passage; модель не определяет доверенные смещения.

Каждый анализ хранит собственный `projectSnapshot`, `requestDocument` и `sourceRevision`. Обновление договора создает новую ревизию. Старый анализ остается историческим: перед его новым review, расчетом или генерацией нужно проверить, что источники актуальны. Изменение трактовки увеличивает review revision и делает прежние расчеты/черновики устаревшими.

## Классификация

| Значение API | Подпись в UI | Значение |
| --- | --- | --- |
| `included` | Explicitly included | Есть поддерживающая формулировка в источнике |
| `excluded` | Explicitly excluded | Есть явная исключающая формулировка |
| `not_specified` | Not explicitly specified | Явного описания не найдено в представленных источниках |
| `ambiguous` | Ambiguous / needs clarification | Формулировка или связь с запросом не позволяет уверенную трактовку |

Отсутствие упоминания не означает исключение и не доказывает право на доплату. Для included/excluded требуется проверяемая contract citation. Каждый извлеченный запрос имеет цитату сообщения клиента, объяснение, unknowns, вопросы и `userReviewRequired: true`. Непроверенная AI-классификация не запускает расчет.

## Подтверждение пользователем

Экран показывает исходный договор, новые запросы, потенциальные изменения и неопределенности. Пользователь подтверждает полный набор item IDs; при изменении классификации указывает причину. Raw analysis остается неизменным, отдельно хранится review. Подтверждение трактовки пользователем не является принятием условий клиентом.

## Финансовый расчет

Все деньги - целые центы USD. Часы вводит пользователь с точностью до двух десятичных знаков. Модель не придумывает часы, ставки, рыночные цены или бюджет клиента.

- Updated hours = original hours + additional hours - removed hours.
- Fixed pricing использует явно введенный signed fee delta.
- Hourly pricing умножает rate cents на net additional hours. Округление до цента выполняется один раз, симметрично от нуля при половине цента.
- Proposed fee = original fee + fee delta; итог не может быть отрицательным.
- Original/updated effective hourly rate - выручка, деленная на часы, до расходов и налогов.
- Additional compensation after expenses вычитает только дополнительные введенные расходы. Это не прибыль всего проекта.
- Deadline extension задается календарными днями, без автоматического учета рабочих дней или юридического толкования срока.

Нулевые дополнительные часы и нулевая доплата допустимы. Исходные/итоговые часы должны быть положительными. Отрицательная fixed delta допустима как явно выбранное снижение цены, если итоговая цена неотрицательна. Отрицательные расходы/ставки/дополнительные часы не допускаются. Removed hours не превышают исходные часы. Scope swap может сохранить оплату и общий объем.

Расчет связан с confirmed review и выбранными item IDs. Он остается предложением и не меняет сохраненный согласованный baseline проекта автоматически.

## Черновики и change order

Тоны: Friendly and collaborative, Clear and professional, Firm but respectful. Генерация требует явного действия; пользователь может редактировать, сохранять и копировать текст. Суммы и сроки берутся из проверенного расчета. Неопределенности и assumptions остаются видимыми. Черновик и change order всегда имеют статус `proposed`, не утверждают принятие клиентом и ничего не отправляют.

Change order содержит проект, исходный scope, предлагаемые изменения, цену, срок, assumptions/dependencies и статус подтверждения. Его можно скопировать как текст. Это редактируемое предложение для обсуждения, не юридическое заключение.

## История и приватность

Новая часть использует существующую подписанную анонимную cookie и отдельные таблицы Postgres. Каждый доступ привязан к server-derived scope; пользователь не передает trusted owner ID. Чужой project/request/draft не должен быть доступен по угаданному UUID. Все API-ответы приватные и не кэшируются.

До отправки в OpenAI пользователь видит disclosure, может отредактировать/скрыть текст и явно запускает анализ. Контракт/сообщения считаются недоверенными данными, а не системными инструкциями. Они не попадают в обычные logs. Внешний API-ключ остается на сервере.

Delete project удаляет его источники, запросы, анализы, подтверждения и черновики в нашем хранилище. UI требует явное подтверждение удаления. Это не обещание удаления данных из логов внешнего AI-провайдера. Cookie действует 30 дней; потеря cookie может лишить доступа к анонимным записям. Автоматическое удаление SQL-строк по сроку cookie нельзя обещать без отдельной реализации.

Повтор с тем же operation ID не должен создавать вторую платную операцию. Измененный текст с тем же ID отклоняется. Незавершенный неоднозначный AI-вызов не перехватывается автоматически другим процессом. Shared daily AI quota учитывает каждое новое фактическое обращение к модели, включая draft generation.

## Связь с обучением

Кнопка **Practice negotiating a change request** открывает существующий `/simulation`. Реальный договор, сообщение клиента и текст анализа не передаются в Practice Mode. Дополнительные персональные параметры требуют отдельного согласия, которого этот срез не предполагает.

## Приемка и выпуск

Нужен сквозной поток на синтетическом договоре с настоящим AI: создание -> анализ -> цитаты -> correction/review -> расчет -> редактируемый draft -> сохранение/повторное чтение -> удаление. Отдельно проверяются cross-session access, malformed AI, injection, stale source/review, duplicate requests и Practice Mode regression. Выпуск только после Node 22 quality checks и браузерной приемки. До этого существующий production сохраняется.
