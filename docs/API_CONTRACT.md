# API contract v1

Источник типов и Zod-схем: `src/types/scope.ts`. Денежные поля содержат целые центы USD: `150000` = $1,500. Часы допускают дробные значения, дни целочисленные. UI переводит центы в доллары только при отображении.

Контракт запроса и успешного ответа v1 сохранен. Реализация ниже относится к `feat/backend-simulation` до слияния PR; `main` пока содержит прежний каркас. Engine и ограниченный английский интерпретатор `rules-v1` работают без LLM. Evaluator не подключен, его массивы пусты. Не представляй этот режим как живой AI. Примеры подключения: `docs/BACKEND_INTEGRATION.md`.

## Общие типы

| Тип | Назначение |
| --- | --- |
| `Scenario` | Серверный сценарий с исходным договором и скрытыми `clientRules` |
| `ScenarioSummary` | Карточка сценария без скрытых правил |
| `PublicScenario` | Исходный договор и публичные события для интерфейса |
| `NegotiationAction` | Проверенный результат интерпретации текста: clarify, propose, accept, decline, unresolved |
| `Agreement` | Предложенное или принятое изменение, связанное с конкретным ходом |
| `ProjectState` | Пересчитанные деньги, часы, срок, активный объём и ID принятых соглашений |
| `NegotiationTurn` | Текст, интерпретация, ответ клиента и соглашение одного хода |
| `EvaluationResult` | Критерии, наблюдаемые доказательства и рекомендации |

Серверный сценарий экспортируется как `websiteProjectScenario` из `src/data/scenarios/website-project.ts`. Это начальная заготовка для Альбины: $1,500, 20 часов, 7 дней, три события. Правила вымышлены и требуют продуктовой проверки.

## GET /api/scenarios

Успех HTTP 200:

```json
{
  "scenarios": [{
    "id": "web-project-01",
    "title": "Sarah Mitchell - Website Project",
    "description": "Practice negotiating scope, delivery dates, and changes to a fixed-fee website project.",
    "clientName": "Sarah Mitchell",
    "currency": "USD",
    "initialFeeCents": 150000,
    "estimatedHours": 20,
    "deadlineDays": 7
  }]
}
```

Использовать `toScenarioSummary(scenario)`.

## GET /api/scenarios/[scenarioId]

HTTP 200: `{ "scenario": PublicScenario }`. Использовать `toPublicScenario(scenario)`, который перечисляет разрешённые поля явно.

`PublicScenario` содержит `id`, `title`, `description`, `clientName`, `currency`, `initialContract` и `events`. В договоре: `feeCents`, `estimatedHours`, `deadlineDays`, `scopeItems`. В событии: `id`, `title`, `clientMessage`, `availableScopeItems`, `learningObjectives`.

Каждый ScopeItem: `{ id, title, description, estimatedHours }`.

События являются публичным описанием задания, а не историей уже полученных сообщений. UI начинает с первого события; переход между событиями определяет серверный движок.

Не отправлять `Scenario` напрямую через JSON и не импортировать серверные данные в client components. Скрытые бюджеты, ограничения и правила оценки не входят в публичный ответ. Это учебная симуляция, исходный код публичный; данный фильтр отделяет клиентский payload от серверных правил, но не обеспечивает секретность открытого репозитория.

Неизвестный ID: HTTP 404, код `SCENARIO_NOT_FOUND`.

## POST /api/negotiate

Запрос:

```json
{
  "scenarioId": "web-project-01",
  "history": [{
    "turnId": "turn-1",
    "eventId": "booking-request",
    "userMessage": "I can add booking for an extra $400 and two more days. Would that work?"
  }]
}
```

`history` содержит всю ветку с начала сценария, включая последний пользовательский ход. `turnId` создаётся один раз через `crypto.randomUUID()` и сохраняется для повторной отправки. Максимум 50 ходов; текст 1-2000 символов после trim. Повторяющиеся `turnId` в одном запросе отклоняются.

Сервер заново загружает неизменяемый исходный договор, проверяет порядок событий, интерпретирует историю и воспроизводит принятые соглашения. Браузер не передаёт доверенные суммы, принятые соглашения или действия. Неизвестные поля запрещены. Изменение применяется один раз, когда engine подтверждает допустимое соглашение. Допустимое предложение может быть принято клиентом в том же ходе; встречное предложение требует отдельного принятия пользователем.

Replay отправляет префикс истории до выбранного момента и новую последовательность ходов. Каждый ход измененного суффикса получает новый `turnId`, даже если его текст совпадает со старым. Это новая ветка, а не дополнение старого результата. Повторная отправка идентичной истории дает тот же результат из исходного договора.

Повторная отправка не создает второе соглашение: экономическое состояние каждый раз строится заново. Дополнительно анонимная cookie-сессия хранит fingerprints истории в памяти одного процесса. Повторное использование `turnId` с другим текстом или префиксом дает HTTP 409 `INVALID_HISTORY`, пока запись есть в этой сессии. Это best-effort проверка конфликтов, а не долговечное хранилище интерпретаций LLM. До подключения LLM стабильные результаты старых ходов нужно сохранять отдельно.

Успешный ответ HTTP 200 задаёт неизмененный `negotiateResponseSchema`:

```ts
{
  scenarioId: string;
  turns: NegotiationTurn[];
  project: ProjectState;
  evaluation: EvaluationResult;
  currentEventId: string | null;
  completed: boolean;
}
```

`turns` содержит все обработанные ходы переданной ветки, включая последний `clientReply`. Сначала UI показывает `clientMessage` первого публичного события. После ответа выбирает следующее публичное событие по `currentEventId`; отдельного поля с новым сообщением нет. Событие меняется только после принятого соглашения или разрешенного отказа. Уточнение, неоднозначный ответ, отклоненное и встречное предложение оставляют событие текущим. При `completed: true` поле `currentEventId` равно `null`.

Заголовки успешного ответа:

| Заголовок | Значение |
| --- | --- |
| `X-ScopeShift-Interpreter` | `rules-v1` |
| `X-ScopeShift-Evaluation` | `pending` |
| `X-ScopeShift-Scenario-Revision` | 16-символьная метка ревизии сценария и правил |
| `Cache-Control` | `no-store` |
| `Vary` | `Cookie` |

Сервер выдает `scopeshift_session` с `HttpOnly`, `Path=/api`, `SameSite=Strict`, сроком 60 минут и `Secure` на HTTPS. Ограничение в памяти процесса: 30 запросов в минуту на известную cookie-сессию. На сессию сохраняется до 256 fingerprints, всего до 500 сессий с LRU-вытеснением. Холодный старт, другой процесс, истечение или замена cookie обходят эти best-effort ограничения. Правильность финансовых расчетов обеспечивается чистым engine и не зависит от cache.

Ошибки:

| HTTP | Код | Причина |
| --- | --- | --- |
| 400 | `INVALID_REQUEST` | Некорректный JSON, схема или повторный `turnId` внутри одного запроса |
| 400 | `INVALID_HISTORY` | Неизвестное событие, неверный порядок или ход после завершения |
| 404 | `SCENARIO_NOT_FOUND` | Неизвестный сценарий |
| 409 | `INVALID_HISTORY` | `turnId` повторно использован с другим текстом или префиксом в известной сессии |
| 413 | `INVALID_REQUEST` | JSON body больше 131072 байт |
| 429 | `RATE_LIMITED` | Превышено ограничение сессии; `Retry-After: 60` |
| 500 | `INTERNAL_ERROR` | Непредвиденная ошибка обработки |

`AI_UNAVAILABLE` остается зарезервированным кодом для будущего provider. Сейчас внешних AI-вызовов нет.

`ScopeChange` содержит `feeDeltaCents`, `deadlineDeltaDays`, `addScopeItemIds`, `removeScopeItemIds`. Дополнительные часы сервер вычисляет по реально добавленным и удалённым ScopeItem. LLM не задаёт часы или итоговую стоимость. Отрицательное изменение цены или срока допустимо в предложении, итог должен удовлетворять правилам сценария и положительной длительности.

`Agreement.status`: proposed, accepted, rejected, counteroffered. Договор меняет только accepted. `sourceTurnId` и `eventId` связывают решение с наблюдаемым действием. `effectiveHourlyRateCents` сервер вычисляет как `Math.round(totalFeeCents / estimatedHours)`; не суммировать округлённые ставки.

`EvaluationResult.criteria` содержит категорию, `earnedPoints`, `maxPoints`, evidence с `turnId`, `ruleId`, `observation` и практический advice. Каждый балл должен иметь проверяемое доказательство. Бесплатная правка или равноценный обмен сами по себе не означают ошибку. Пока evaluator не подключен, возвращается `{ criteria: [], strengths: [], improvements: [] }`; это незавершенная оценка, а не нулевой результат ученика.

## Формат ошибки

```ts
{ error: { code: string; message: string } }
```

Коды перечислены в `apiErrorSchema`. Не передавать stack trace, ключи провайдера или скрытые ограничения в ответе об ошибке.

## Правила совместимости

1. Данила владеет общими типами и API. Любое изменение формы сначала согласовать с Арсеном и Альбиной.
2. Арсен строит UI по публичным типам; заглушки показывает с явной отметкой и не выдаёт их за настоящий AI.
3. Альбина расширяет сценарий и тесты, сохраняя идентификаторы либо согласуя миграцию.
4. Ни один участник не дублирует определения типов локально.
