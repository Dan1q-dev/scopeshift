## Архитектура

Один Next.js 16 App Router проект: React, TypeScript, Tailwind CSS, Zod, Vitest и Playwright. Node.js 22 (>=22.12, в пределах ветки 22.x). Frontend и Route Handlers используют одни контракты.

Motion и shadcn/ui пока не установлены. Добавление зависимостей и изменение lockfile согласуй с Данилой.

1. AI интерпретирует сообщение и формирует реплику клиента.
2. Детерминированный TypeScript engine проверяет правила сценария.
3. Только принятое соглашение меняет деньги, часы, сроки и scope.
4. Оценка объясняет результат через действия и правила сценария.

Не доверяй итоговым суммам, часам и решениям, пришедшим из браузера или LLM. Сервер восстанавливает состояние из исходного сценария и проверенной истории. Повторный запрос не должен повторно начислять одно соглашение. Replay должен воспроизводить историю, а не подменять цифры.

## Контракты и данные

- Источник типов: `src/types/scope.ts`. Источник HTTP-контракта: `docs/API_CONTRACT.md`.
- Используй существующий клиентский адаптер `src/lib/client/api.ts`: `getScenarios`, `getScenario`, `negotiate`, `ScopeShiftApiError`.
- Не создавай несовместимые локальные копии `Scenario`, `ProjectState`, `Agreement` и других общих типов.
- Скрытые правила клиента и секреты остаются на сервере. Не импортируй полный серверный сценарий в клиентские компоненты.
- Макеты и fixtures допустимы для параллельной разработки, если явно помечены. Не представляй их как работающий AI или завершенную интеграцию.
- Тексты продукта и pitch на английском; командная документация может быть на русском.
- Никогда не используй длинные тире U+2014 и U+2013. Используй обычный дефис `-`.

Текущий каркас отдает каталог и публичный сценарий через GET API. Корректный `POST /api/negotiate` возвращает HTTP 501 до реализации engine и AI. Ключ для запуска каркаса не нужен; имена в `.env.example` пока зарезервированы и не используются.

## Проверка перед PR

Выполни `npm run typecheck`, `npm run lint`, `npm test` и `npm run build`. Для изменений пользовательского потока добавь или обнови соответствующие проверки, когда поток реализован.

В PR укажи: что пользователь теперь может сделать, какие файлы и контракты затронуты, что проверено и что пока не готово. Небольшие законченные PR предпочтительнее большого слияния в последний час.

Секреты храни только в локальном окружении и настройках деплоя. Не коммить `.env.local`, токены, реальные клиентские данные или ключи. Не используй `NEXT_PUBLIC_*` для секретов. Перед коммитом проверь `git diff --cached`.

## Приоритет и критерий готовности

Сначала полный цикл одного сценария: исходный договор, запрос клиента, ответ пользователя, решение клиента, изменение проекта и объяснимый результат. Затем Replay, Compare и Change Order. Голос и дополнительные сценарии идут после стабильного основного потока.

Функция готова, когда проверена в интегрированном приложении. Успешная сборка сама по себе не доказывает работу продукта. Не заявляй реализованную функцию, AI-интеграцию, деплой или результат тестирования без проверки.
